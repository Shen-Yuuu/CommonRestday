# 同休日：HarmonyOS API 26 及以下能力与精简版优化调研

> 调研日期：2026-09-21  
> 目标基线：`docs/prototype/index.html` 的 **01「温暖编辑感」精简版**  
> 范围：信息架构、页面布局、组件与交互、系统触达、隐私安全、本地数据、后台与云端、跨设备、无障碍和性能  
> 版本口径：优先写 HarmonyOS API Level；新版本同时保留官方 SemVer，例如 `26.0.0`。所有候选能力的起始版本均不高于 API 26。

---

## 0. 结论先行

当前精简版的正确方向不是继续在首页堆功能，而是把核心闭环做深：

```text
一眼知道何时有空
    ↓
展开一个共同窗口
    ↓
共同确认 / 创建计划
    ↓
写入系统日历或设置提醒
    ↓
通过桌面卡片、通知再次触达
```

建议优先落地以下 8 项：

1. **首页只保留三个答案，并让主结果直达详情**：使用 `Navigation + NavDestination` 管理层级；结果卡到窗口详情采用轻量共享元素或系统转场。
2. **共同时间改成“周时间带 + 窗口详情半模态”**：周视图负责比较，`bindSheet` 负责确认、写日历、提醒和分享，避免再开一整页表单。
3. **系统日历作为默认计划出口**：优先用 `CalendarManager.editEvent()` 拉起系统编辑页，用户确认后写入，权限和信任成本都比静默写入低。
4. **提醒采用分层策略**：普通状态更新用 Notification Kit；精确时间提醒优先依托系统日历；只有确有“应用退出后仍准点提醒”的必要时才申请代理提醒权益。
5. **配对入口变成二维码 + 系统分享，短码兜底**：`Scan Kit + Share Kit` 能显著减少输入错误，并让“面对面配对 / 异地配对”各有自然路径。
6. **增加一张桌面服务卡片**：只展示“下一个完整同休日 / 今晚是否能吃饭 / 距离开始多久”，点击直达共同时间详情；不要把完整班表搬上桌面。
7. **数据仍以本地 RDB 为真源**：Preferences 只保存轻量设置，HUKS 管理本机密钥；云端仅同步可重建的加密快照，任何云故障不阻断本机代录。
8. **API 26 做渐进增强**：`ContainerReader` 做组件级断点，`ChipV2` 改善筛选项语义，系统沉浸材质只用于弹窗/底栏，Senior Mode 状态用于增大热区与简化信息；低版本必须保留 `GridRow/mediaquery`、普通 Chip 与暖色实体表面回退。

### 不建议现在做

- 不用 `WorkScheduler` 承担准点约会提醒；它是“满足条件后由系统统一调度”的延迟任务，不保证精确时刻。
- 不用分布式 KV 代替情侣跨账号云同步；它更适合同一用户设备协同，无法替代当前的邀请码、访问控制和云快照模型。
- 不为一次计算长期开启长时后台任务；共同时间重算应在前台或 TaskPool 中短时完成。
- 不把 API 26 沉浸光感铺满暖色编辑界面；它更适合弹窗、选择器和浮动底栏，过量使用会破坏“纸面感”，并增加 GPU 开销。

## 2. 建议后的精简版信息架构

严格沿用 01 精简原型的 **3 个底部一级入口**。班表不重新升回第 4 个 Tab，而是作为“我的”中的高频二级页；这样既保留原型的精简程度，也不牺牲编辑效率。

| 层级 | 页面 | 只回答什么 | 不再承担什么 |
|---|---|---|---|
| 一级 Tab | 同休（首页） | 今晚能否一起、下个完整同休日、最近能否出行 | 班表编辑、复杂筛选、同步设置 |
| 一级 Tab | 共同时间 | 哪天、几点到几点共同空闲；有哪些已创建计划 | 伴侣管理、完整日历账户管理 |
| 一级 Tab | 我的 | 伴侣与同步、作息参数、提醒偏好、数据与隐私 | 重复展示共同时间结果 |
| 二级页 | 班表与班次 | 快速录入本人/TA 的工作与课程，并处理例外 | 独占底部导航、展示长篇计算说明 |

二级体验统一成三种容器：

- **详情页 `NavDestination`**：需要深阅读或可被深链直达的内容，如某个共同窗口、配对状态、数据管理。
- **半模态 `bindSheet`**：短流程，如筛选、编辑一段班次、创建计划、提醒选项。
- **系统面板/系统应用**：分享、扫码、日历编辑、通知授权，不再自制一套低可信替代 UI。

## 3. 按页面与用户旅程组织的能力建议

## 3.1 启动与首页：先看到答案，再决定是否展开

### A. `Navigation` / `NavDestination` 统一页面层级

| 项 | 内容 |
|---|---|
| API 起始版本 | `Navigation` API 8；`NavigationMode` API 9；导航栏宽度范围 API 10 |
| 放入位置 | 首页结果卡 → 共同窗口详情；“我的”→ 配对/数据详情；班表 → 模板编辑 |
| 设计方式 | 手机保持 Stack；宽屏/折叠展开态自动变成 Split，左侧列表、右侧窗口详情 |
| 收益 | 返回栈、系统转场、宽屏双栏统一；避免手写页面显隐和状态丢失 |
| 风险 | 不要同时在 `NavDestination` 根节点叠加 `zIndex/transition/geometryTransition`，会扰乱默认转场；自定义动效放到内容节点 |
| 官方依据 | [Navigation 常见问题](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/arkts-navigation-faq) |

### B. 响应式布局：API 26 `ContainerReader` + 低版本回退

| 项 | 内容 |
|---|---|
| API 起始版本 | `ContainerReader` API 26.0.0；`GridRow/GridCol` API 9；`mediaquery.matchMediaSync` API 7 |
| 放入位置 | 首页三答案卡、共同时间周视图、我的页设置组、平板双栏 |
| 设计方式 | `< 360vp` 单列紧凑；`360–599vp` 标准手机；`600–839vp` 结果与摘要双列；`≥840vp` 左侧导航 + 主内容。API 26 按组件容器宽度判断，低版本按窗口断点判断 |
| 收益 | 分屏、自由窗口、折叠屏和横屏时不再仅“放大手机稿”；组件放在不同容器中也能自行适配 |
| 风险 | `ContainerReader` 仅 API 26；必须有 `GridRow/mediaquery` 回退，不能把最低兼容版本整体抬到 26 |
| 官方依据 | [容器断点 ContainerReader](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/arkts-layout-development-container-reader) |

### C. 首页内容编排

建议首页首屏固定顺序：

1. 日期与伴侣状态（极轻量，不做大卡片）；
2. 主答案：“今晚 18:40–21:30 可以一起”；
3. 两条次答案：“下个完整同休日”“最近可出行窗口”；
4. 仅在有问题时出现冲突/缺数据条；
5. 一条“查看本周共同时间”入口。

主卡片点击后以 `Navigation` 进入窗口详情；不要把“创建计划、写日历、提醒、分享”四个按钮同时摆在首页，它们统一收进详情半模态。

### D. API 26 Senior Mode 渐进适配

| 项 | 内容 |
|---|---|
| API 起始版本 | `accessibility.isSeniorModeEnabled()` / `onSeniorModeStateChange()`：API 26.0.0 |
| 放入位置 | 全局，尤其首页答案、底部导航、班表格子与弹层按钮 |
| 适配策略 | 系统开启长辈模式时：正文至少提高一级、热区增至 48vp 左右、隐藏装饰性副文案、周视图默认切换为“日列表”而非高密度时间网格 |
| 收益 | 对大字体、低视力和不熟悉复杂时间轴的用户更友好；同一个信息架构可切换为低认知负担版本 |
| 风险 | 监听必须使用命名函数并在生命周期结束前 `off`，本机 API 26 声明明确提示不注销可能造成内存泄漏或崩溃 |
| 官方依据 | [获取长辈模式状态](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/eldercare-description) |

## 3.2 共同时间：从“结果列表”升级为可操作的时间对象

### A. 周时间带作为主视图，列表作为无障碍/窄屏回退

建议保留原型已有的课程表式时间带，但明确两种呈现：

- 标准手机：横向 7 天、纵向时间轴；点击色块展开详情。
- 窄屏、大字/长辈模式、屏幕朗读：按天分组的 `List + ListItemGroup`，每项直接朗读“周六 10:00 到 18:00，共 8 小时，完整同休日”。

`List` 自 API 7 可用；大列表采用 `LazyForEach` 或带虚拟滚动的 `Repeat`，再用 `cachedCount` 做合理预加载。官方明确指出 `ForEach` 会一次创建所有子节点，而懒加载可降低启动耗时和内存。[List API 与性能说明](https://developer.huawei.com/consumer/cn/doc/doccenter-references/api/ts-container-list)

### B. `CalendarPicker`、`DatePicker`、`TimePicker` 用于边界输入

| 项 | 内容 |
|---|---|
| API 起始版本 | `CalendarPicker` API 10；`DatePicker/TimePicker` API 8 |
| 放入位置 | 共同时间日期跳转、计划日期与时间、班表例外日期 |
| 收益 | 与系统日期/时间习惯一致，自动获得焦点、语言和部分无障碍能力；替代手写滚轮或文本时间输入 |
| 设计建议 | 周视图顶部点击日期印章弹出 `CalendarPicker`；创建计划时日期沿用窗口日期，只让用户调整标题、地点和提醒 |
| 风险 | 选择器用于“选择日期”，不是完整月历热力图；共同空闲密度仍需业务自绘/自组装 |
| 官方依据 | [CalendarPicker API](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V14/ts-basic-components-calendarpicker-V14) |

### C. API 26 / 状态管理 V2 组件的选用边界

本机 API 26 SDK 已包含 `ChipV2`、`DatePickerComponent`，API 18 起已有 `SegmentButtonV2`。它们适合替换原型中重复出现的基础交互，但不应替换具有品牌识别度的主答案卡和时间带。

| 组件 | 起始 API | 放入位置 | 价值 | 回退与取舍 |
|---|---:|---|---|---|
| `ChipV2` | 26.0.0 | “全部 / 完整同休日 / ≥24 小时”等筛选，隐私范围选择 | 自带选中、图标和无障碍配置，减少自制 Chip 的状态遗漏 | 低版本回退普通 Chip/自定义按钮；继续使用暖纸色和小圆角，不套默认视觉即可 |
| `TabSegmentButtonV2` / `CapsuleSegmentButtonV2` | 18 | “窗口 / 计划”“列表 / 周历”“我 / TA” | 双向状态、镜像、字体缩放和无障碍行为更完整 | 若现阶段仍使用状态管理 V1，可先用普通 `SegmentButton`，不为一个控件强推全页迁移 |
| `DatePickerComponent` | 26.0.0 | 未来统一日期、日期时间与区间选择 | 可以减少多套 Picker 外观和校验逻辑 | 当前官方 API 目录仍标注 Beta；P0 继续用稳定的 `CalendarPicker + DatePicker/TimePicker` |

结论：API 26 新组件是**基础控件质量升级**，不是重新增加功能或页面。优先替换筛选和选择器，主视觉仍由原型的自定义组件承担。

### D. `bindSheet` 做“窗口详情 / 创建计划”

| 项 | 内容 |
|---|---|
| API 起始版本 | API 10 |
| 放入位置 | 点击共同时间色块；首页点击主答案；班表点击某天 |
| 内容结构 | 拖拽条 → 日期/时长 → 双方空闲依据 → 计划标题/地点 → “加入系统日历”主按钮 → 提醒/分享次操作 |
| 收益 | 保留上层时间背景，用户不会失去上下文；符合“短流程不离页”的精简原则 |
| 风险 | 键盘弹出、横屏和大字体需验证 sheet 高度；破坏性动作不放在首屏主按钮 |
| 官方依据 | [ArkUI 全局接口与 UIContext 迁移](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/arkts-global-interface-V13) |

### E. `ListItem.swipeAction` 用于计划管理

| 项 | 内容 |
|---|---|
| API 起始版本 | API 9 |
| 放入位置 | “已创建计划”列表 |
| 交互 | 左滑显示“编辑 / 删除”；删除后 Toast 提供短时撤销；点击主体进入详情 |
| 收益 | 降低卡片按钮密度，又保留高频管理效率 |
| 风险 | 滑动动作不可作为唯一入口，屏幕朗读和键盘场景必须在详情菜单保留同等操作 |
| 官方依据 | [ListItem `swipeAction`](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/api/ts-container-listitem) |

## 3.3 从共同窗口到真实安排：日历、提醒和通知

### A. Calendar Kit：优先走用户确认的系统编辑页

| 项 | 内容 |
|---|---|
| API 起始版本 | `CalendarManager` / `Calendar.addEvent` API 10；`CalendarManager.editEvent(event)` API 12 |
| 放入位置 | 窗口详情 Sheet 的主按钮“加入系统日历” |
| 推荐路径 | 默认调用 `editEvent(event)` 打开系统日历编辑页，由用户确认标题、时间、地点和提醒；高级设置中才提供直接写入 |
| 收益 | 把“共同空闲”真正变成系统日程；系统日历可继续承担提醒、跨设备日历同步和用户编辑 |
| 权限/风险 | 直接创建/查询日历涉及 `READ_CALENDAR`、`WRITE_CALENDAR`（或 whole calendar）权限；必须按需申请。事件 ID 要落本地，后续修改/删除要避免产生重复日程 |
| 官方依据 | [Calendar Kit API 入口](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V14/calendar-arkts-V14)、[Calendar Kit 错误码](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/calendar-arkts-errorcode) |

建议事件模型：

- 标题默认“和 TA 的共同时间”，允许一键换成“晚饭 / 约会 / 出行 / 自定义”；
- 描述只记录共同窗口来源与本地窗口 ID，不写入完整班表；
- 结束时间不得超出共同窗口；用户强行超出时展示冲突提示但不阻止保存；
- 本地保存 `calendarEventId + windowFingerprint`，班表变化后只提示“原计划与新班表冲突”，不静默改系统日历。

### B. Notification Kit：状态触达，不冒充准点闹钟

| 项 | 内容 |
|---|---|
| API 起始版本 | `publish` / `requestEnableNotification` API 9；`isNotificationEnabled` Promise 形态 API 11 |
| 放入位置 | 配对成功、同步失败、班表变更导致计划冲突、计划即将开始（非严格准点场景） |
| 收益 | 用户不打开应用也能获知有意义的状态变化；点击通知深链到具体窗口/冲突详情 |
| 权限/风险 | 首次应在用户开启“提醒我”后再解释并请求通知授权；禁止把每次后台同步都发成通知；同一事项使用稳定 notificationId 更新而不是堆叠 |
| 官方依据 | [取消通知（含 Notification Kit 调用范式）](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V5/notification-cancel-V5) |

### C. 代理提醒：可选增强，不作为 P0 硬依赖

| 项 | 内容 |
|---|---|
| API 起始版本 | `reminderAgentManager.publishReminder` API 9；排除日期 API 12；更新提醒 API 20 |
| 放入位置 | 用户对某个已创建计划显式开启“准点提醒”时 |
| 收益 | 应用退到后台甚至进程终止后，系统仍可代理倒计时/日历/闹钟提醒 |
| 权限/前置 | `ohos.permission.PUBLISH_AGENT_REMINDER` + 通知授权；手机/平板/PC 存在管控，需要在 AGC 申请开放能力，审批后重新生成 Profile 并手动签名 |
| 数量限制 | API 26.0.0 起普通应用最多 64 个有效/未过期提醒；API 25 及以下最多 30 个 |
| 产品风险 | 资格申请、通知打扰、提醒上限和用户关闭通知都可能使能力不可用；所以默认仍建议系统日历，代理提醒只做显式可选项 |
| 官方依据 | [代理提醒（ArkTS）](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/agent-powered-reminder) |

### D. 正确的后台能力分工

| 场景 | 应使用 | 不应使用 |
|---|---|---|
| 保存前的短计算/加密 | 前台异步或 TaskPool | 长时任务 |
| App 刚退后台，收尾上传小快照 | 短时任务 `requestSuspendDelay`（API 9） | 无限重试 |
| 非实时、满足网络/充电条件再维护 | WorkScheduler 延迟任务（API 9） | 对用户承诺精确执行时间 |
| 精确日程提醒 | 系统日历 / 获批后的代理提醒 | WorkScheduler |
| 持续可感知的数据传输 | 仅确有业务必要时的长时任务 | 仅为“保活”而开启 |

官方把延迟任务定义为满足条件后进入系统队列、单次回调最长运行 2 分钟；代理提醒才是闹钟/倒计时/日历类能力。见 [后台任务合理使用](https://developer.huawei.com/consumer/cn/doc/doccenter-app-quality/bpta-use-of-background-tasks)。

## 3.4 班表录入：减少填写，不增加解释

### A. 三段式录入，而不是一张大表单

1. **选择对象**：我 / TA；
2. **选择模板**：白班、夜班、休息、自定义；
3. **应用范围**：当天、连续日期、循环序列。

短流程使用 `bindSheet`，日期使用 `CalendarPicker`，时间使用 `TimePicker`。录入完成后立即在底部显示自然语言预览：“9 月 22–24 日，08:30–17:30，上班”。

### B. Grid + 手势用于批量涂抹，但必须有替代入口

| 项 | 内容 |
|---|---|
| API 起始版本 | `Grid/GridItem` API 7；组合手势与 `animateTo` API 7 |
| 放入位置 | 班表月视图批量标记、模板排序 |
| 收益 | 连续夜班/休息日可通过长按进入编辑、拖动涂抹，减少逐日点按 |
| 风险 | 复杂拖拽仅作为效率增强；必须保留“选择起止日期”表单路径。拖拽时给出视觉和轻触觉反馈，离开有效区域不提交 |
| 官方依据 | [Grid 网格元素拖拽](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/arkts-grid-element-drag-exchange) |

### C. 撤销优先于二次确认

新增/修改班次直接提交并用 Toast 提供“撤销”；只有覆盖大量日期、清空班表、解除配对等不可轻易恢复操作才弹确认框。这样比每次保存都弹 Dialog 更符合高频录入。

### D. 触觉反馈

`vibrator.startVibration` 自 API 9 可用，需要 `ohos.permission.VIBRATE`。仅用于：

- 长按进入批量涂抹；
- 拖过新日期格；
- 保存成功的一次轻反馈；
- 冲突/越界的一次警示反馈。

调用前可检查设备是否支持具体效果；禁止在滚动和普通点击中滥用。API 12 提供常见 `HapticFeedback` 枚举。本机 SDK 声明指出不同设备效果不同，应视为增强而非业务状态证明。

## 3.5 伴侣配对：二维码、系统分享和短码三条路径

### A. 面对面：Scan Kit 扫码

| 项 | 内容 |
|---|---|
| API 起始版本 | 默认扫码 `startScanForResult` API 11（Scan Kit 模块基础能力 API 10）；二维码生成 `createBarcode` API 11 |
| 放入位置 | “我的 → 配对同步 → 面对面配对” |
| 流程 | A 生成一次性二维码 → B 调起系统默认扫码页 → 预览对方昵称与可见范围 → 双方确认 → 云端完成配对 |
| 收益 | 消除邀请码手输错误；默认扫码 UI 自带对焦、曝光和多码选择，开发成本低 |
| 权限/限制 | 使用默认扫码 UI；官方默认界面会处理相机授权/隐私提示，但不支持浮窗/分屏，Scan Kit 当前也不支持模拟器，必须真机验证 |
| 安全 | 二维码只放一次性 token / 短链，不放班表、密钥明文或永久 pairId；短时过期、使用一次即失效 |

API 26 新增 `scanCore.isDefaultScanSupported()` / `isCustomScanSupported()`。进入配对页先做能力检查：支持时展示“扫码配对”，不支持时直接突出“输入短码”，不要让用户点击后才看到失败。

### B. 异地：Share Kit 系统分享面板

| 项 | 内容 |
|---|---|
| API 起始版本 | `systemShare.SharedData` / `ShareController.show`：API 11 |
| 放入位置 | “邀请 TA”主按钮；窗口详情“分享这个时间” |
| 分享内容 | 配对：一次性安全链接 + 短码；共同窗口：可读摘要，不附完整班表 |
| 收益 | 自动适配手机模态面板、横屏/展开态对话框、平板锚点弹窗；复用用户熟悉的分享渠道 |
| 限制 | SharedData 至少一条记录，最多 500 条，总大小 200KB；缩略图有大小约束。不要把加密快照塞进分享面板 |
| 官方依据 | [分享文本](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/share-utd-text) |

### C. 短码仍保留为离线/兼容兜底

- 6–8 位人类可读码分组展示，例如 `M7Q2-K9`；
- 输入自动大写、忽略连字符和空格；
- 粘贴只在用户主动点击时读取；不监听剪贴板变化；
- 复制的邀请码设置合理失效期，配对成功后立即作废。

系统剪贴板 `getSystemPasteboard()` 自 API 6 可用，`PasteData.shareOption` 自 API 9 可设置传播范围。邀请码属于敏感临时数据，能用二维码/系统分享时不要强迫用户复制粘贴。

### D. 深链与 App Linking 承接

在 `module.json5` 的 UIAbility `skills.uris` 中声明窄范围 URI，只匹配配对落地页，例如 `commonrestday://pair/<token>`。收到链接后必须先解析、校验来源与过期时间，再进入“确认配对”，不能点开即绑定。URI 配置字段与匹配规则见 [应用链接说明](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/app-uri-config)。

异地邀请进一步可接 App Linking：

- 已安装应用：HTTPS 链接直接打开“确认配对”页；
- 未安装应用：先进入应用市场，安装首次启动后用 `deferredLink.popDeferredLink()` 恢复链接；
- 本机 SDK 声明显示延迟链接自 API 15 可用，只在系统缓存 **10 分钟**且只能取一次，所以它只能优化“立即安装”的链路，不能替代服务端邀请码 TTL 和手动短码兜底；
- 需要 AGC 申请链接前缀、配置可信域名与应用包信息，建议在云端配对基础流程稳定后再接入。

官方能力说明见 [App Linking Kit](https://developer.huawei.com/consumer/cn/agconnect/App-linking)。

## 3.6 桌面与锁屏触达：服务卡片而不是常驻通知

### A. 推荐一张“下一个共同时间”ArkTS 服务卡片

| 项 | 内容 |
|---|---|
| API 起始版本 | FormExtensionAbility / `formProvider.updateForm` API 9；`FormLink` API 10 |
| 展示位置 | 桌面、锁屏等系统入口（普通应用内不能嵌卡片） |
| 卡片内容 | 上半：下个完整同休日日期；下半：最近共同窗口与倒计时；状态角标：本地/已同步/待更新 |
| 交互 | 点击整卡直达共同时间；“创建计划”直达选中窗口；不在卡片内编辑班表 |
| 收益 | 用户无需打开 App 就能看到最核心答案，符合本产品低频但高价值的使用特征 |
| 约束 | 卡片尺寸和组件/动效能力受限；卡片 UI 与提供方进程隔离，数据通过 `updateForm`；后台更新频率受系统管控 |
| 官方依据 | [Form Kit 简介](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/formkit-overview-V13)、[ArkTS 卡片生命周期](https://developer.huawei.com/consumer/en/doc/harmonyos-guides-V5/arkts-ui-widget-lifecycle-V5)、[FormLink](https://developer.huawei.com/consumer/cn/doc/harmonyos-references-V13/ts-container-formlink-V13) |

### B. 刷新策略

- 冷启动、班表变更、配对同步成功后主动 `updateForm`；
- 用系统定时/定点刷新更新“今天/明天”文案，不做秒级倒计时；
- 云端 Push 刷新以后再评估。官方对工具/效率类卡片 Push 有每日额度，不适合把每次同步都推到桌面。[ArkTS 卡片 Push 刷新](https://developer.huawei.com/consumer/en/doc/harmonyos-guides/arkts-ui-widget-update-by-push)

### C. API 20 Live Form 暂缓

`LiveFormExtensionAbility` 自 API 20 提供交互式服务卡片 UI，它与 Live View（实况窗）不是同一能力。当前卡片只需要“看结果 + 深链到 App”，静态 ArkTS 卡片配合 `FormLink` 已足够；只有未来需要在卡片内部完成更丰富、持续的交互时再评估 Live Form，避免无必要的生命周期与资源成本。[Form Kit API 20 变更](https://developer.huawei.com/consumer/en/doc/harmonyos-releases/js-apidiff-formkit-6001)

### D. Live View 当前不适配，Intents Kit 只作远期入口

- **Live View Kit（API 11 起）**面向有明确开始/结束、短时、持续变化且用户主动触发的进行中活动，并仍处于 Beta 和场景准入阶段；官方还限制最长 8 小时、手机/平板、中国境内及真机使用。“未来哪天有共同时间”不是进行中活动，因此不应为了系统曝光强行套实况窗。若以后出现“正在共同出行，实时显示剩余行程”的独立场景，再重新评估。[Live View Kit 简介](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/liveview-introduction-V13)
- **Intents Kit / InsightIntent（API 10 起）**可把“查看下个共同休息日”“创建晚饭计划”接入小艺建议、本地搜索或对话任务。它需要意图注册、开放 API 和足够稳定的动作模型，且不应共享伴侣班表明细；建议等主闭环和隐私模型稳定后再做 P3 入口增强。[Intents Kit](https://developer.huawei.com/consumer/cn/sdk/intents-kit)

## 3.7 “我的”、本地数据与隐私

### A. RDB 管事实数据，Preferences 管偏好

| 能力 | API 起始版本 | 应保存内容 | 不应保存内容 |
|---|---:|---|---|
| `relationalStore` RDB | 9 | 班次区间、课程、计划、同步版本、日历事件映射、变更日志 | UI 临时展开状态 |
| `preferences` | 9 | 最短共同时间、起床/通勤缓冲、主题、提醒开关、上次同步时间 | 大数组、班表真源、密钥明文 |

RDB 基于 SQLite，提供 CRUD、谓词和事务。批量展开轮班模板必须放进事务，避免只写一半；高数据量查询应分批并移出 UI 主线程。官方建议单次查询不超过 5000 条，并可在 TaskPool 中查询。[RelationalStore API](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/api/arkts-apis-data-relationalstore)

### B. 数据库加密 + HUKS 密钥托管

| 项 | 内容 |
|---|---|
| API 起始版本 | HUKS ArkTS 核心接口 API 9；AES/HKDF 等规格更早已有，当前 ArkTS 以 API 9 接口为基线 |
| 放入位置 | 无独立页面；“我的 → 数据与隐私”只展示状态和清除入口 |
| 方案 | RDB 开启加密；数据库密钥和云快照主密钥由 HUKS 按别名生成/托管；云端只保存加密 payload |
| 收益 | 不把长期密钥写进 Preferences/源码；HUKS 在安全环境中完成密钥生命周期和密码运算 |
| 风险 | 密钥别名、用途、算法参数要稳定；密钥丢失即无法解密，必须明确恢复/重配对策略。邀请码不应直接长期充当数据库主密钥 |
| 官方依据 | [HUKS 密钥使用流程](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/huks-key-use-overview)、[密钥导入安全边界](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/huks-key-import-overview-V13)、[ArkData 加密库 FAQ](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/data-faq?ha_source=202512yk&ha_sourceId=89000503) |

### C. 数据管理页必须有四个明确动作

1. 导出我的数据；
2. 清除本机数据；
3. 解除配对并删除云端配对数据；
4. 查看最近同步状态与失败原因。

“解除配对”与“清除本机”必须分开，防止误以为清本机就会删云端。云端删除仍需业务自行级联，因为现有云开发调研未发现一键注销级联 API。

### D. 系统备份恢复

`BackupExtensionAbility` 自 API 10 可接入应用数据备份/恢复框架，适用于换机和应用迁移。普通应用只能声明和定制哪些数据允许备份，**不能自行触发系统备份**。建议：

- 可备份：非敏感 UI 偏好、班表数据库的加密备份或可重建数据；
- 谨慎/不备份：一次性邀请码、云会话、HUKS 私密密钥材料；
- 恢复后若密钥不可用，应提示重新配对，不要生成看似成功但无法解密的状态。

官方说明见 [应用数据备份恢复概述](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/app-file-backup-overview)。

## 3.8 云端配对、后台同步与跨设备

### A. 云端策略沿用“低频加密快照”

结合 `05-云端配对前置条件调研.md`，建议保持：

- 本地 RDB 永远是真源；
- 云端只放按 `pairId + ownerUid + version` 标识的加密快照；
- `pairId/ownerUid` 为安全规则所需的最少明文字段，班表 payload 加密；
- 冷启动、进入共同时间、班表保存后做条件同步；
- 网络失败只展示“待同步”，不阻塞查看与本机代录；
- 解除配对时删除云函数、云数据库相关记录，并清本机云会话。

Cloud Foundation Kit `cloudFunction.call()` 起始 API 12，需要 `ohos.permission.INTERNET`；客户端超时应显式收敛到云函数同步调用上限内。官方入口：[调用云函数](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/cloudfoundation-call-function)、[云数据库服务](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/cloudfoundation-database-service)。

### B. 同步状态的 UI 只需要四态

| 状态 | 呈现 | 操作 |
|---|---|---|
| 仅本机 | “数据只在这台手机” | 邀请配对 |
| 已同步 | “刚刚同步”弱提示 | 查看详情 |
| 待同步 | 云朵/小圆点，不弹打扰通知 | 立即同步 |
| 需处理 | “配对已失效 / 数据冲突” | 打开修复页 |

不要显示数据库、函数或错误栈术语。冲突页只回答：哪一方更新、影响哪些日期、保留哪份或合并。

### C. WorkScheduler 只能做机会性维护

可用于“有网络且设备状态合适时上传待同步快照/执行每周云心跳”，但不能承诺一定在某一时刻执行，也不能作为唯一保活措施。每次冷启动和用户主动同步仍应完成一次有效调用；WorkScheduler 只是补充。

### D. 跨设备连续性排在跨账号同步之后

Ability Continuation/分布式能力可让同一用户在手机、平板/PC 间继续查看共同时间，但它解决的是“同一用户换设备”，不是“两位伴侣跨账号协作”。建议顺序：

1. 先把云端双人快照同步稳定；
2. 再让 `Navigation` 和响应式布局适配平板/折叠屏；
3. 最后评估跨设备续接当前窗口详情。

不要把 Distributed KV Store 作为伴侣配对替代品，否则身份边界、撤销、跨账号和服务端访问规则都会变得含糊。

## 3.9 动效、材质与响应：保留“温暖编辑感”的鸿蒙实现

### A. 动效层级

| 层级 | 推荐能力 | 用在何处 | 建议时长 |
|---|---|---|---:|
| 微反馈 | `animateTo`（API 7） | chip、按钮按压、班表选中 | 120–220ms |
| 内容变化 | `transition` / opacity + translate | 首页答案更新、空状态替换 | 220–360ms |
| 空间连续 | `geometryTransition`（API 7） | 首页主答案 → 窗口详情中的日期/时长 | 320–480ms |
| 系统层级 | Navigation 默认转场、bindSheet | 页面推进与半模态 | 优先系统默认 |

原则：只给“状态因果”加动效。后台同步、页面首屏的每张卡片不必轮流飞入；共同时间色块从选中到详情可以保留一镜到底。官方指出 90Hz 下每帧预算约 11.1ms，并建议统一状态更新、优先图形变换属性。[动画性能优化](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-animation-usage-guide)

### B. API 26 沉浸光感只用于浮层

| 项 | 内容 |
|---|---|
| API 起始版本 | `uiMaterial` / `systemMaterial`：API 26.0.0 |
| 推荐位置 | `bindSheet`、Calendar/TimePickerDialog、AlertDialog、底部浮动导航（若采用） |
| 视觉策略 | 选择较厚材质并做暖色赋色，使其像半透明描图纸覆盖在象牙纸面上；普通内容卡仍用实体暖色表面 |
| 收益 | 系统自动适配深浅色和设备算力；弹层层级更清晰，按压可有形变/流光反馈 |
| 风险 | 需要 targetSDKVersion ≥ 26.0.0；占用较多 GPU；低版本必须使用暖色实体 sheet/dialog 回退；不得为了材质牺牲文字对比度 |
| 官方依据 | [沉浸光感简介](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-immersive-light-sense-overview)、[开启沉浸光感](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/arkts-immersive-light-sense-enable) |

### C. 安全区与沉浸式

首页暖色背景可以延伸到状态栏，但文字、日期印章和返回按钮必须留在安全区。底部 TabBar 背景可延伸到导航区，交互热区不能被手势区遮挡。官方方案包括 `expandSafeArea` 和窗口避让区监听，见 [窗口沉浸式](https://developer.huawei.com/consumer/cn/doc/HarmonyOS-Guides/immersive-window-feature)。

## 3.10 无障碍与可用性

### A. 组件语义

ArkUI 通用无障碍属性建议：

- `accessibilityText`（API 12）：给纯图标按钮、颜色块补充可朗读名称；
- `accessibilityDescription`（API 10）：说明操作后果，例如“删除后可在 5 秒内撤销”；
- `accessibilityLevel`（API 12）：隐藏纸张颗粒、装饰图形等无意义节点；
- 将“日期 + 时间 + 标签”组合成一个朗读单元，不让读屏逐字符穿过时间轴。

Accessibility Kit 的能力范围与 ArkUI 语义关系见 [Accessibility Kit 简介](https://developer.huawei.com/consumer/en/doc/harmonyos-guides-V5/accessibilitykit-overview-V5)。

### B. 不只靠颜色传达班次与共同空闲

- 自己 / TA / 共同空闲分别配合轮廓、纹理或图标；
- 冲突状态增加文字“冲突”，不是只变红；
- 色块点击后的详情需朗读完整时间、双方状态和可用操作；
- 深色主题重新校验文本、禁用态和莓红强调色对比度。

### C. 字体、热区与输入

- 正文使用 `fp` 并允许系统字体缩放；关键卡片避免固定高度；
- 普通触控热区至少约 40vp，主操作与长辈模式建议 48vp；
- API 26 将 Button、Button 模式 Toggle、Select、Chip、ChipGroup 的默认最小命中高度提高到 32vp，但这只是框架兜底，不取代上述 40/48vp 的产品设计目标；
- 360vp、小窗、横屏、2 倍字体分别测试无横向滚动和按钮遮挡；
- 重要操作支持键盘焦点顺序与回车触发，拖拽/滑动必须有按钮替代。

命中区域行为见 [ArkUI 触摸热区设置](https://developer.huawei.com/consumer/cn/doc/doccenter-references/api/ts-universal-attributes-touch-target)。

## 3.11 性能与稳定性

### A. TaskPool 下放共同时间计算

| 项 | 内容 |
|---|---|
| API 起始版本 | TaskPool API 9；`Priority.IDLE` API 12 |
| 放入位置 | 120 天窗口展开、班表归一化、双方区间求交、云快照加解密/序列化 |
| 收益 | 避免保存班表后主线程卡顿；计算完成后一次性提交 UI 状态 |
| 风险 | 任务存在调度/序列化成本，短小计算留在主线程；子线程不能操作 UI 或依赖主线程 Context；控制并发度 |
| 官方依据 | [TaskPool 使用规范](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/task-pool-usage-guidelines) |

### B. 列表与周视图

- 共同窗口/计划长列表用 `List + LazyForEach/Repeat`，合理 `cachedCount`；
- key 使用稳定业务 ID，不用数组索引或 `JSON.stringify`；
- 不在同方向 Scroll 中嵌一个未限定主轴尺寸的 List，否则懒加载可能失效；
- 120 天时间轴不要一次构建全部 ArkUI 节点，按可视周/月分片；
- 周视图若自绘，只更新变化日期的图层，不因同步时间文本刷新整个页面。

### C. 状态更新

- 首页三个答案来自一个不可变计算快照，避免三处各自重算；
- 同步状态和相对时间与班表数据分离，防止“刚刚同步”每分钟触发整页刷新；
- API 23+ 可评估状态管理 V2；但不要为了升级装饰器改变已验证的数据真源。

## 5. 建议的页面级改造清单

### 首页

- 保留三个答案，主答案整卡可点；
- 伴侣/同步状态压成标题旁小状态，不另占大卡；
- 缺数据时只给一个主动作“补全班表”；
- 宽屏把三个答案变成 2+1 栅格，不简单拉宽；
- API 26 可让标题栏/底栏使用轻材质，内容卡仍保持暖纸感。

### 共同时间

- 顶部：周范围 + CalendarPicker；
- 主体：周时间带，窄屏/大字模式回退日列表；
- 底部：已创建计划；
- 点击窗口：bindSheet 展开，主动作“加入系统日历”；
- 计划冲突：在原位置显示红色文字标签，点击查看“为什么冲突”。

### 班表

- 顶部本人/TA segmented control；
- 中部月视图或连续日期列表；
- 底部固定“添加班次”主按钮；
- 添加 Sheet 采用对象 → 模板 → 日期范围三段式；
- 批量涂抹为增强能力，随时可撤销；
- 保存后 TaskPool 重算，在主按钮附近显示短暂进度，不全屏 loading。

### 我的

- 第一组：伴侣状态，主按钮按状态变化为“邀请 TA / 查看同步 / 修复配对”；
- 第二组：共同时间规则（最小时长、作息缓冲）；
- 第三组：提醒与桌面卡片；
- 第四组：数据与隐私；
- 把调试性云参数、技术错误码藏进诊断详情，不出现在普通设置页。

### 配对

- 首屏两大选择：“面对面扫码”“分享邀请”；
- 手动输入短码作为文本次入口；
- 二次确认页展示昵称、头像占位、可见范围、邀请码失效时间；
- 配对完成后只展示“已配对 + 最近同步”，不继续暴露邀请码。

## 6. 需要明确排除或降级的能力

| 能力 | 结论 | 原因 |
|---|---|---|
| WorkScheduler 准点提醒 | 排除 | 延迟任务由系统调度，不能承诺某时刻执行 |
| 长时后台保活 | 排除 | 与低频时间规划场景不匹配，耗电且需要用户可感知 |
| Distributed KV 作为情侣同步 | 排除 | 不能替代跨账号身份、安全规则与撤销模型 |
| 静默批量写系统日历 | 默认关闭 | 权限重、容易制造重复事件；先用系统编辑页确认 |
| 全页面 API 26 玻璃材质 | 排除 | 与 01 暖纸风冲突、GPU 成本高、低端表现不稳定 |
| 首页常驻同步日志 | 排除 | 技术状态压过核心答案；只在异常时显现 |
| 每次同步都通知 | 排除 | 打扰高且没有用户价值；仅通知需行动的变化 |
| 用 Live View 展示未来共同时间 | 排除 | 不是短时、进行中且持续变化的活动，并受 Beta/场景准入限制 |
| 卡片显示完整班表 | 排除 | 信息密度、隐私和卡片更新成本都过高 |
| 把二维码内容直接当长期密钥 | 排除 | 泄露面和生命周期不可控；仅承载短时一次性凭据 |

## 8. 验收清单

### 核心体验

- 首页 5 秒内能回答“今晚 / 下个完整同休日 / 最近能否出行”；
- 从首页主答案到系统日历编辑不超过 3 次点击；
- 面对面配对不需要键盘，异地配对不要求手抄短码；
- 云端断网时，本机代录、计算、查看、创建日历事件仍可工作；
- 班表变化导致计划冲突时，不静默改计划，有可解释提示。

### 响应与无障碍

- 360vp、标准手机、横屏、600vp 分屏、平板宽屏布局无横向溢出；
- 系统字体放大到约 2 倍时，关键时间、主按钮和底部导航不截断；
- 屏幕朗读能一次读出日期、时间段、时长、标签和按钮后果；
- 颜色关闭/灰度下仍能区分本人、TA、共同空闲与冲突；
- 拖拽、滑动操作都有按钮替代路径。

### 性能与后台

- 班表保存后共同时间重算不阻塞 UI；
- 120 天数据不一次创建全部可视节点；
- WorkScheduler 未执行也不会丢数据或漏掉用户已承诺的准点提醒；
- 服务卡片无秒级刷新、无持续后台保活；
- API 26 材质关闭或低版本设备上仍有完整实体表面回退。

### 隐私与安全

- 邀请二维码/链接一次性、短时有效且不含班表明文；
- 密钥不存源码、日志、Preferences 或二维码；
- 解除配对与清本机数据是两个明确操作；
- 导出/分享默认只含用户选择的摘要，不含完整伴侣班表；
- 通知、日历、相机等权限在功能触发时解释并请求，拒绝后仍有降级路径。

## 10. 最终产品判断

鸿蒙能力对这个项目最大的价值不是“让页面更像系统应用”，而是把一个低频工具变成**自然融入系统时间与桌面入口的共同生活助手**：

- ArkUI 负责让温暖编辑风在小屏、分屏、折叠屏和大字体下仍然成立；
- Calendar / Reminder / Notification 负责让共同时间成为真正会发生的安排；
- Form Kit 负责让答案无需打开 App 也能被看到；
- Scan / Share 负责让双人关系建立得足够轻；
- RDB / HUKS / Cloud Foundation 负责让数据本地可靠、云端可恢复但不反客为主；
- Accessibility / TaskPool 负责让体验不只“好看”，而是可达、流畅、长期可维护。

若只选一个后续原型方向，应先制作完整的“**首页主答案 → 窗口详情 Sheet → 系统日历确认 → 桌面卡片回显**”链路。它能同时验证信息架构、组件层级、系统能力和产品价值，是本轮调研中收益最高、依赖最少的组合。
