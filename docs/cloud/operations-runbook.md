## 1. 一次性前置（开通前核对，缺一不可）

| # | 事项 | 为什么是硬条件 | 出处 |
|---|---|---|---|
| 1 | 账号已实名认证、注册地为中国境内（港澳台除外）、**账户无欠款** | 欠款会连带卡住云开发开通；开通靠 DevEco 勾选协议自动完成 | docs/05 §1 |
| 2 | 数据处理位置只启用「中国」，之后**不再改动** | 云开发仅支持中国境内；更改或取消启用**可能自动清理云侧数据且不可恢复** | docs/05 §3.3 |
| 3 | 手动开启**消费提醒 + 余额不足提醒** | 免费档"用尽即停"不会自动扣费也不会自动扩容；配额提醒只有互动中心消息是默认有的 | docs/05 §3.1 |
| 4 | 项目区域、运行时锁定 **Node.js 20** | 2025-11-04 起云函数运行时收窄为仅 Node.js；不要沿用旧 `@hw-agconnect` SDK 写法 | docs/05 §8 |
| 5 | 记录项目 ID / 应用 ID 与 `CloudProgram/cloud-config.json` 的存放位置 | HarmonyOS NEXT 端云一体化的云侧配置是 `cloud-config.json`，**不存在** `agconnect-services.json` 这个文件 | docs/05 §5 |
| 6 | 云数据库 schema 落在 `resources/rawfile`，缺失会报 `schemaJson_ is empty` | 部署顺序错了就会得到这个报错，别当成 API 问题 | docs/05 §5 |

**免费额度**（按月/按天重置，非一次性试用）：云函数请求 100 万次/月、内存时长 40 万 GB-s/月、出流量 5 GB/月；云数据库存储 1 GB/月、出站 10 GB/月、对象读/写/删 50000/20000/20000 次/**每天**、同时连接 150、每秒操作 10。双人低频场景实测占用量级约为月请求配额的 0.01%（docs/05 §2.1），**容量不是问题，闲置回收才是**。

## 2. 部署

### 2.1 部署顺序（错了会白跑）

1. 云数据库：建对象类型（`PairSession`、`PairMember`、`PairSnapshot`）→ 生成对象类型文件 → 建存储区 → 引入 rawfile → 部署 schema；
2. **安全规则先写后部署数据**：三条默认拒绝，任何"先放开再收紧"都会留下可被索引的窗口；
3. 云函数：按 §2.3 的 8 个函数逐个部署，先 `pair-heartbeat`（最简单，用来验通链路）再 `pairing-*` 最后 `snapshot-*`；
4. 端侧：关联签名配置 → 模拟器取 `clouddevelopproxy.debugToken` 注册到 AGC（模拟器无登录态，缺这步必然失败）→ 真机走一次 `pairing-create`。

### 2.2 安全规则（唯一允许的数据访问口径）

- `PairSnapshot`：`request.auth.uid == resource.ownerUid || request.auth.uid == resource.peerUid`，且**读写都只经云函数**；
- `PairSession` / `PairMember`：仅成员可读，仅创建者可改状态；
- 端侧直连必须被拒（预期错误 `2001015: permission denied`）。这是"端侧不得直连云数据库"的唯一实现方式——它是规则约束，不是 API 缺失，所以**默认拒绝**是配置项而不是可选项；
- 每次改动规则后跑一次协议 §4.8 的越权用例（第三设备读快照必须 403）。

### 2.3 函数清单与资源建议

| 函数 | 触发方 | 频率 | 内存/超时建议 | 写库 |
|---|---|---|---|---|
| `pairing-create` | 用户动作 | 极低 | 128MB / 10s | 会话、成员 |
| `pairing-join` | 用户动作 | 极低 | 128MB / 10s | 会话 |
| `pairing-confirm` | 用户动作 | 极低 | 128MB / 10s | 会话 |
| `pairing-status` | 打开设置页 | 低 | 128MB / 5s | 只读 |
| `pairing-unpair` | 用户动作 | 极低 | 128MB / 15s | 删除（级联，须在一次调用内完成） |
| `pair-heartbeat` | 冷启动 + 每周 | **最高** | 128MB / 5s | 不写库 |
| `snapshot-put` | 日程变更后（合并窗口 5s） | 低 | 256MB / 20s | 单对象覆盖写 |
| `snapshot-get` | 回前台 / 进入共同时间 | 低 | 128MB / 10s | 只读 |

- 云函数同步调用上限 55s，端侧统一 `timeout: 30000`（协议 §3.3）；函数内部超时之和必须 < 30s，否则客户端先断、服务端还在写，会得到"失败但已写入"的假不一致；
- `snapshot-put` 的体积阈值按协议 §4.7 的 2 MB 拒绝，函数内**不解密、不解析明文**；
- 版本策略：端侧按协议用 `version` 参数固定调用 `$latest` 以外的显式版本，回滚＝切回上一版本号（§5）。

## 3. 日常巡检（每周一次，10 分钟）

| 看什么 | 在哪看 | 触发动作 |
|---|---|---|
| 三项服务的免费额度与已用量 | 项目设置 → 项目配额 | 任一项 > 60% → 查异常调用源（§4.5） |
| 云函数错误率与 P95 耗时 | 云函数监控 | 错误率 > 1% 或 P95 > 3s → §4 |
| `pair-heartbeat` 调用量 | 云函数监控 | **连续 7 天为 0** → 心跳没跑起来，距闲置回收还有约 5 个月，立刻修 |
| 数据库对象数 | 云数据库 | 与配对用户数不对账（>2×）→ 解除配对级联删除有漏 |
| 项目最后活跃时间 | `pair-heartbeat` 响应的 `projectLastActiveAt` | 临近 6 个月 → 主动发一次调用，别等预警 30 日 |

闲置回收是本产品**最容易踩**的运维风险：双人低频意味着一个寒假不打开就可能触发（docs/05 §3.2）。心跳的作用是把"项目级活跃"和"用户级活跃"解耦——只要还有任何一个用户在用，项目就不会被回收。

## 4. 故障手册

### 4.1 端侧 `CloudApiError(1001)`（AGC 未初始化/未开通）

错误码来源：`201`（缺 INTERNET 权限）、`1008210009`（客户端内部错误）、`1008211001`（服务端错误）。
排查顺序：签名配置是否与云工程关联 → 模拟器是否注册 debugToken → `cloud-config.json` 是否存在且项目 ID 正确 → rawfile schema 是否部署。
**端侧行为已定：一律降级本机，不重试、不弹窗轰炸。**

### 4.2 `1008210001`（网络连接错误）

映射为 `retryable = true` 的网络类错误。用户侧网络问题占绝大多数，不告警；只有**同时段大面积**出现才查云函数可用区。

### 4.3 `2001015: permission denied`

两种可能，必须区分：
- 出现在**端侧直连**路径 → 预期行为，说明规则生效，改代码走云函数；
- 出现在**云函数内部** → 规则写错或成员表未建好，属**部署缺陷**，立即回滚规则（§5）。

### 4.4 `QUOTA_EXHAUSTED` / 配额用尽

免费档用尽即停（不自动扩容、不自动扣费）。处置：
1. 当天停止排同步（客户端已按 `retryable = true` 只做 3 次退避，不会打爆）；
2. 查调用源：最常见是心跳被写成了每次进 App 都发，或 `snapshot-get` 没有 `sinceVersion` 导致全量拉取；
3. **不要**为绕过配额而升级按量付费——降级到"今天不同步"对本产品完全可接受（主路径是本机代录）。

### 4.5 异常调用放大（疑似被刷）

症状：云函数请求量突增、数据库对象读暴涨、出现非成员 `FORBIDDEN`。
处置顺序：`pairing-*` 与 `snapshot-*` 加限流（按 uid 每分钟上限）→ 撤销可疑会话（`pairing-unpair`）→ **重新生成会话密钥口径**（协议 §6 的别名批量删除）→ 通知受影响用户重新配对。
注意：载荷是加密的，被刷的最坏后果是配额耗尽与元数据（uid/pairId/version）暴露，不是日程泄露。

### 4.6 「已配对但看不到对方数据」

按顺序判：`pairing-status` 是否 `ACTIVE` → 对方 `version` 是否 0（对方从没推过）→ 本机是否解密失败（密钥失配，协议 §7）→ 本机是否把 `snapshot-get` 的 `null`（无更新）当成错误。
**禁止的处置**：为了让界面有内容而伪造对方数据，或在解密失败时自动重建密钥。

### 4.7 云侧完全不可用

预期表现：本机录入、共同时间计算、计划、冲突全部正常，只有「伴侣与同步」显示降级。
这是验收项（`docs/testing-checklist.md` §9.3），不是事故。真正的事件是"云端故障导致本机功能变慢或崩溃"——那是降级路径有洞，按缺陷处理。

## 5. 回滚

| 对象 | 回滚方式 | 数据影响 |
|---|---|---|
| 云函数 | 切端侧调用的版本号回上一版 | 无 |
| 云数据库 schema | **禁止破坏性回滚**；只允许向前兼容加字段 | 回滚列删除会丢快照 |
| 安全规则 | 回上一版规则文件并复跑越权用例 | 无 |
| 配对能力（总开关） | 端侧 `FeatureFlags.cloudPairing = false` 重新出包 | 云侧数据保留；本机数据不受影响 |

停服＝把 `cloudPairing` 关回 `false`，**不需要**删云数据：删数据是不可逆动作，而关开关已经能让全部用户回到本机代录主路径。确需清除某个 pair 的数据时走 `pairing-unpair`；确需清除全部数据时删除整个项目（不可恢复，需二次确认并先导出配置）。

## 6. 隐私审计（每次改动后必做一次）

从云数据库导出 `PairSnapshot` 的全部明文列，确认：

- [ ] 明文列只有 `pairId / ownerUid / peerUid / version / shareLevel / schemaVersion / updatedAt / algorithm`（协议 §5.2 允许清单）；
- [ ] `ciphertext` 里搜不到任何日程名、课程名、地点、备注、计划标题、昵称（抽样解密 3 份人工核对，确认这些字段根本没进明文体）；
- [ ] 云函数日志（含 `console.log`）**不打印** `code`、`payload`、A 的明文、任何密钥或别名；
- [ ] 没有任何"邀请历史"表——协议设计上 `code` 不落库留存，只用即时状态；
- [ ] 快照只保留每 `pairId + ownerUid` 的**最后一个**版本（无历史版本堆积）。

审计发现任一违规 → 视同密钥泄露处理：批量撤销配对、通知用户重新配对，并在协议文档记录事件。
