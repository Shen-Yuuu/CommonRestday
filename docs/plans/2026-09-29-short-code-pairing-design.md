# 六位短码配对闭环设计

日期：2026-09-29。用户已选择「只分享六位短码，邀请方在应用内确认」；二维码、配对链接及扫码入口不参与该流程。

## 已核实的现状与取舍

当前 `pairing.join` 只把会话推进 `PENDING_CONFIRM`，并把 `confirmToken` 交给加入方。邀请方必须经二维码或链接收到它才能调用 `confirm`，而邀请方界面没有接收入口，因此两台设备会停在待确认。云对象里的 `uid` 来自调用参数，不能单凭它证明调用者就是邀请方；六位码也不能单独授权读取伴侣日程。

考虑过三条路径：① 六位码输入后直接激活，最省步骤但允许猜码者抢占配对；② 更长的高熵码输入后直接激活，安全性较好但手输成本高；③ 六位码只发起加入，邀请方在本机明确确认。采用用户批准的③。一次性确认凭据改在 `create` 时生成、仅返回邀请方，在本机以 HUKS 密钥加密保存；`join` 不再返回它。邀请方确认时才调用云端 `confirm`。凭据从不进入二维码、链接、明文 Preferences、日志或剪贴板。

## 交互与状态

1. A 点「生成配对码」：云端创建 `WAITING` 会话、六位码和确认凭据；A 安全保存凭据并显示短码。
2. B 输入短码：云端一次性认领会话并写入 B 的公钥，转 `PENDING_CONFIRM`；B 本地完成 ECDH，但仍不得推快照，页面提示等待 A 确认。
3. A 点「检查配对状态」：看到待确认申请，显示确认框；A 点「确认配对」后带本机保存的凭据调用 `confirm`。成功且能与 B 公钥协商后，A 才显示已配对。
4. B 点「检查配对状态」：云端为 `ACTIVE` 且本机配对密钥存在后才显示已配对。两端的快照推拉随后按原共享等级规则运行。

不持续轮询云端；进入本页和回前台可刷新本地状态，但是否查云端由用户的「检查配对状态」明确触发，以保护项目级免费配额。页面删除二维码、配对链接、扫码、系统分享与深链确认；保留复制六位码。旧版本生成的待确认会话没有邀请方本地凭据，不能自动升级成新流程；要求取消并重新生成。已 `ACTIVE` 的会话不受影响。

## 失败与清理

云端 `create` 成功但本机凭据密封失败时，不写本机 `pairId/WAITING`，提示重新生成；下一次 `create` 会作废同一创建方的旧开放会话。`join` 的密钥协商失败时本机不宣称已配对。`confirm` 云端成功但本机密钥协商失败时保留可修复的本地状态，`reconcilePair` 依云端 `ACTIVE` 补齐密钥。取消、解除、清空数据均擦除邀请凭据的本地密文和 HUKS 别名；过期、重复使用、断网都不伪报成功。

## 验收边界

离线断言覆盖：只有 `create` 回确认凭据、`join/status` 不回；无凭据不可确认；邀请方确认后 `ACTIVE`、加入方对账后 `PAIRED`；短码错误/过期/重复使用与失败回滚；页面无二维码和链接。编译与离线门禁由本轮完成。云对象重新部署、两台 API 26 模拟器真实配对与 AGC 行状态核对由用户完成，未实测之前不把设备格标绿。
