# 共同计划：双向确认与后台／锁屏通知设计

定稿：2026-10-04。依据用户在 10 月 3 日同意的建议，并明确要求覆盖应用未打开和锁屏场景。

## 1. 范围与现状

本设计重新开启此前暂缓的双向共确方向，取代“只共享预览”的首发目标。现有程序仍是本地计划与班表快照同步；本文不是已实现功能的说明。不得把现有计划自动转成邀请，不得把收到班表快照当作双方确认。

- 单人／本机代录：继续直接创建本地计划。
- 云配对：点击“发送邀请”，对方同意后才成为共同计划。
- 新建、接受、拒绝、撤回、改期与取消走独立共同计划通道，不塞进 CRD1 班表快照。
- 通知使用华为 Push Kit 的系统通知消息，覆盖应用未打开与锁屏；应用内反馈只是补充。
- 不为此强制新增华为账号登录页；可先验证 AGC 匿名认证，但必须有服务端可校验的身份。

## 2. 状态与参与计算

| 状态 | 发起方看到 | 接收方看到 | 是否占用时间 |
| --- | --- | --- | --- |
| 本机待发送 | 尚未发送，可重试 | 不可见 | 否 |
| PENDING | 等待 TA 确认，可撤回 | 待我确认，可同意／暂不安排 | 否 |
| ACCEPTED | 已确认 | 已确认 | 是，双方各一份 |
| DECLINED | TA 暂不安排 | 已拒绝 | 否 |
| WITHDRAWN | 已撤回 | 邀请已撤回 | 否 |
| EXPIRED | 邀请已过期 | 邀请已过期 | 否 |
| CANCELLED | 计划已取消 | 计划已取消 | 否 |

发起邀请即表达发起方同意，不再要求发起方确认第二次。接收方同意必须获得服务端提交结果；离线点击不显示“已确认”，不提前占用时间。请求超时属于结果不确定，先按同一 requestId 查询／重试，不能另建重复邀请。

发送前和同意前检查最新本机可用数据；尚未同步的数据明确提示，不能声称实时核验了两台离线设备。邀请开始时间已过去时不能再确认。云端使用独立固定保留期限清理陈旧邀请，不假装能够读取密文里的开始时间。

## 3. 页面表现

“共同 → 计划”分为“待我确认”“等待 TA”“已确认”，另显示本机待发送和必要的终态记录。使用用户给 TA 设置的本机名字，未命名显示 TA。

- 待确认卡突出日期、起止时间、类型和标题；动作是“同意”“暂不安排”。
- 发起方待确认卡提供“撤回”；已确认卡提供改期和取消。
- 任一尚待双方确认的邀请存在时，计划 tab 右上角显示玫红圆点；仅打开 tab 不消失，状态真正离开 PENDING 后才消失。
- 本机待发送有独立文字状态，不能伪装为对方已收到；同步失败沿用“我的”页集中反馈和手动重试。
- 未确认邀请不出现在今日安排、忙碌区、日程周历、共同空闲计算和系统日历中。
- 前台收到邀请可轻提示，不强制打断正在编辑的页面；通知点击后定位相应计划。

## 4. 身份与并发是前置门槛

### 4.1 身份不能只认客户端 UID

现有云对象以客户端提交的 uid 查会话成员。这并不证明是谁点击“同意”；应用签名校验也不等于用户身份校验。双方持有同一配对加密密钥，因此不能仅凭共享密钥签名来区分双方的确认动作。

新通道必须通过服务端验证的认证令牌，取得认证主体，并在安全的创建／加入流程中绑定到会话成员。服务端固定项目范围，不接受客户端自行指定可信项目或成员身份。匿名认证不代表匿名直连数据库，也不代表可以省略令牌验证。

旧配对不得仅凭 pairId＋旧 uid 自动绑定认证主体。安全升级需证明原成员的独立凭据所有权，或经双方明确同意重新建立安全会话；没有经过验证的升级方案时，旧配对保留原功能，但共同计划入口不可用。新安全会话的解除、清库和密钥更换也不能被旧 uid 接口绕过。

本机 Server SDK 1.0.5 有 verifyAccessToken({ accessToken, checkRevoked: true })。这只证明有实施方向；必须隔离验证真实令牌、错误项目、过期／撤销与两台设备的独立身份。

### 4.2 真正的条件提交

同意、撤回、拒绝、改期和取消必须在事务内校验 stateVersion，写入结果、幂等请求账和通知事件。普通“先查版本再 upsert”不是原子比较，不允许当作并发保护。

SDK 有 collection.runTransaction 与 Transaction.executeQuery/executeUpsert。先在隔离表做真实双请求竞争：两请求读同一个版本，只有一个提交，另一个返回冲突。离线桩通过不能代替此证据。

## 5. 独立云协议与加密

拟定新对象（最终字段需按 CloudDB 类型约束落稿）：

| 对象 | 职责 |
| --- | --- |
| PairMemberBinding | 可信认证主体与安全配对成员绑定 |
| PairDatePlan | 邀请密文、状态、内容版本、状态版本、发起／接收角色 |
| PairPlanRequest | requestId 的已提交结果，防重复请求 |
| PairPushTarget | 本人设备推送 token 与有效状态，不对伴侣公开 |
| PairPlanOutbox | 已提交状态产生的通知事件与投递状态 |

保持班表快照 schemaVersion=2，不为共同计划强行抬高 CRD1。独立 planProtocolVersion=1，并要求双方能力可确认；一方旧版本不支持时不允许发送“无法确认”的邀请。

标题、类型、实际起止时间继续端到端加密。公开元数据限于必要的身份引用、ID、角色、状态、版本及服务端创建／更新时间／清理期限。服务端不能解密，所以不得宣称服务端验证了计划落在双方共同空闲中。

AAD 定为 `FT_DATEPLAN|pairId|planId|contentRevision|planProtocolVersion`。contentRevision 只随内容修改变化；stateVersion 随同意／撤回等状态变化。不能把密文绑定到 stateVersion，否则服务端改变状态后将无法重新加密，双方也无法解密原内容。

邀请是一次主动分享其标题与时间：即便平时选择“只共享空闲”，也应在发送处说明这次将向 TA 分享邀请内容，不能隐式升级所有日程的共享等级。

## 6. 本地投影、改期与冲突

本地独立缓存所有邀请状态，只有 ACCEPTED 投影到活动计划。稳定映射为 `shared:<pairId>:<planId>`，重复拉取只更新一行，不重复写系统日历。

已确认计划改期产生新内容修订的待确认提案；原已确认时段继续生效。对方同意后原子替换双方活动时段；拒绝／撤回改期不影响原计划。双方都可取消已经确认的共同计划，取消后同步移除活动投影，保留必要历史状态。

“已确认”与“后来日程冲突”是两个维度。后来新增班次导致冲突时提示调整，不能自动把双方已达成的同意抹掉。

现有班表快照会合并计划忙碌区。双端都落地同一个共同计划后，不能把对方快照里的同一段再算成第三方冲突。正确处理是在快照构建、区间合并之前排除新共同计划投影，由共同计划通道在各自本机参与计算。不得从已经合并的忙碌区直接减去共同计划，否则会连重叠的上班／课程一起误删。新投影语义须有能力标记；旧快照不可假装具备该语义。

## 7. 系统日历与推送

### 7.1 日历独立授权

双方确认只决定应用内共同计划。写系统日历仍由每台设备的用户独立确认。对方同意不代表授权写入对方系统日历。日历拒绝、取消或不可用时保留已确认共同计划，常驻显示“仅保存在应用内”，不能回滚云端同意。

### 7.2 系统通知闭环

通知默认文案只说明“有一条共同计划待确认”“共同计划已确认”“共同计划有更新”，锁屏默认不泄露标题、具体行程和时间。

1. 用户主动启用通知时申请系统通知权限，取得 Push Kit token。
2. 服务端校验本人认证身份后登记 token；不得让客户端指定另一成员的推送接收者。
3. 邀请／确认状态提交时，在同一事务中留下稳定 eventId 的通知事件。
4. 服务端发送鸿蒙通知消息；失败不撤销已提交的邀请或同意。
5. 使用稳定事件标识、受支持的通知折叠参数和端侧去重，减少重复；不得承诺外部网络投递恰好一次。
6. 点通知／回前台／手动刷新后拉取权威状态。通知不是授权依据，不能直接根据消息内容创建活动计划。

应用未打开与锁屏提示依赖设备通知权限、网络、系统设置、免打扰、推送权益和签名。不得承诺必达、强制响铃或解锁；系统通知不等于后台自动重算。静默／后台消息不能代替系统通知。

推送服务端凭据只放服务端配置，不进 HAP、仓库或聊天。使用当前鸿蒙 Push v3 接口，不混用 Android Push v1 或服务时间线接口。云端通知重试只能是明确部署的有界任务；现有客户端“次日自动重试”不恢复，客户端失败保留手动重试。

## 8. 生命周期、兼容与隐私

解除配对级联处理共同计划、请求记录、推送目标及事件。删除失败保留最小可用补删凭据，但不能把旧的裸 uid 当作新安全会话的删除授权。清库、恢复备份、认证会话丢失时必须重新核验认证绑定；旧 token 不得继续接收该成员通知。

升级不得丢失旧本地计划、系统日历清理句柄、已有补删账或班表。能力暂不可确认时不发送新邀请、不消耗业务版本号，也不显示已接通。

隐私政策需增加共同计划共享、认证标识、推送 token、通知权限、服务商、用途、保存期限及删除路径。随包全文、MD、HTML 保持一致；AGC 托管稿由用户重新生成／发布，不能仅修改仓库便声称托管页已更新。
