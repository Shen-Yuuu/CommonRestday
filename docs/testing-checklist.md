## 0. 三种证据口径

三种口径不能互相替代，也不能互相冒充。

| 口径 | 怎么跑 | 能证明 | 当前状态 |
|---|---|---|---|
| 离线单测 | `node tools/test/run.mjs`（日志 `tools/test/out/last-run.log`，失败返回非零） | 领域引擎、读模型、用例编排的口径正确 | **155 passed / 0 failed**（2026-09-22 复跑） |
| 真机插桩 | `entry/src/ohosTest`（DevEco 的 OhosTest 运行配置） | 真实 RDB / Preferences 上写进去的数据，能被下一次查询按同一口径读回来 | 编译通过（`hvigor --mode module -p module=entry@ohosTest assembleHap` → BUILD SUCCESSFUL），**未执行 → 待设备** |
| 手工走查 | 下面 §1–§9 | 系统弹窗、权限、真实日历、渲染、热区、读屏 | **全部待设备** |

**任何"待设备"项不得因为前一种口径通过而勾掉。**

### 0.1 插桩用例覆盖什么

`entry/src/ohosTest/ets/test/Ability.test.ets`，describe 名 `ActsAbilityTest`：

- [ ] `uiability_launch_leaves_a_valid_window_cache`：拉起真实 `EntryAbility` 后，内置班次就绪、冷启动重算把窗口缓存写成有效值（US6 / FR-011）。
- [ ] `home_answer_points_at_a_window_the_page_offers`：首页答案指向的那段空闲，必须在共同时间页的窗口里能找到（同源，否则点进去是空的）。
- [ ] `plan_occupies_explains_reschedules_and_frees_the_slot`：建计划 → 时段被占用 → 日程变更把计划标成冲突并给归因 → 采用替代时间（日历事件随之迁移）→ 撤销变更自动回到已确认 → 取消后时段恢复空闲。每一步的断言都来自**下一次查询**，不是当次返回值。

**插桩刻意不覆盖的三件事**（不要在插桩里判通过）：

1. **真实系统日历确认页**——要人手点一次「保存」，见 §6。插桩把日历端口换成确定性假实现（`bindCapabilities`），因此它证明的是"本应用侧的投影编排"，不是"系统日历里真的有那条日程"。
2. **通知栏**——提醒端口恒返回 `-1`（不注册系统提醒），验收不往通知栏塞东西。真实提醒策略在阶段 4.3。
3. **云端快照**——`CLOUD_BLOCKED`，见 §9。

**造冲突的口径差异**：改造文档的场景写的是"修改课程制造冲突"。手工走查按 §7 用课程；插桩用的是"临时班次类型 + 单日覆盖"，因为课程展开依赖学期锚点与节次表，那是本机真实数据，测试不该动。两者落到引擎里是同一条判定（都是"我的忙碌"），归因文案不同（`与你的课程冲突` / `与你的班次冲突`）。

**执行方式**：仓库里的 `entry/src/ohosTest` 只有 `ets/test/List.test.ets` 与 `ets/test/Ability.test.ets`，**没有 testrunner 入口文件**。本轮只做到"插桩包编译通过"，因此不要照抄 `aa test -s unittest OpenHarmonyTestRunner` 当成可用命令——设备接入后先用 DevEco 的 OhosTest 运行配置跑通，再把确认过的命令行补回本节。

**残留数据**：插桩跑完会清掉临时班次类型 `test-e2e-fullday`、临时单日覆盖并取消计划；但计划表没有硬删除，库里会留一条标题为 `E2E 阶段2验收计划`、状态 `CANCELLED` 的行——一眼能认出是验收数据，需要干净现场就执行一次 §1 的 `bm clean`。

## 7. 冲突：解释、替代、保留、恢复（阶段 2 出口）

**制造冲突**：先在共同窗口里建一条计划（如周六 15:00–18:00），再到「我的 → 课程表」手动添加一门**覆盖计划起点**的周六课程（或把那天临时改成整天班）。

- [ ] 7.1 保存后**无需手动刷新**：计划自动标为冲突，首页与共同计划分段同时出现提示
- [ ] 7.2 归因文案与真实原因一致，逐条对照：
  - 覆盖来自课程 → `与你的课程冲突`
  - 覆盖来自班次/单日改班 → `与你的班次冲突`
  - 计划落在自己作息时段外 → `落在你的作息时段外`
  - 本机代录的对方日程压上来 → `TA 的这段时间已有安排`（**不是** `对方时间发生变化`）
  - 双方都变（我的 + 对方同时压住） → `与你的安排冲突，对方时间也发生了变化`；受影响时段给交叠更大的那一侧
  - 老数据（无归因）→ `与日程冲突`（这是兼容兜底，新建计划不该走到这里）
- [ ] 7.3 冲突详情把**受影响时段**与**替代时段**分开说，不把两段混成一个时间范围
- [ ] 7.4 `对方时间发生变化` 与首页红点 `对方时间发生变化` 在单人/本机代录下**不该出现**：这条归因只在对方数据来自云端位图快照（标签恒为 `BUSY`）时才成立，而快照链路受 `CLOUD_BLOCKED` 门禁关闭。若真机看到它，说明有人在无快照的情况下编造了对方语义 → 判失败
- [ ] 7.5 **隐私负例**：任何归因文案都不得替对方说出具体课程名/班次名（本机代录能给原因码，也只说"TA 的这段时间已有安排"）；L1/L2 粗粒度快照下只能得到 `对方时间发生变化`——那半边等阶段 3 门禁解除后再验
- [ ] 7.6 `改到替代时间` → 确认页显示 `新时间：…` 与 `系统日历日程与提醒会一并更新` → 确认 → `已改期（…）`：计划落到替代窗口，系统日历里旧事件消失、新事件存在（真机确认）
- [ ] 7.7 替代窗口在点击前已失效（先改班表让它没了）→ 提示 `替代窗口已失效，请重新选择时间` 或 `替代窗口太短，请重新选择时间`，**计划仍在原时间**，不出现半改状态
- [ ] 7.8 改期已落库但日历写入失败 → 计划保留新时间，卡片显示可重试的「写入日历」，不回滚、不假装成功
- [ ] 7.9 `保留原计划` → `已按原时间保留，不再提示改期`：同一条冲突不再重复弹替代建议；等日程再变（冲突签名不同）时重新提示
- [ ] 7.10 `重新选窗口` → 跳到窗口分段去另找时间
- [ ] 7.11 撤销造成冲突的课程/班表改动 → 计划自动回到 `已确认`、冲突文案清空（用户不用再点一次）
- [ ] 7.12 没有未来可用替代窗口时提示 `未来暂无合适的替代窗口，可以保留原计划或另找时间`，`暂无替代时段` 而不是伪造一个时间

## 8. 渲染与可访问性门禁（四条各一组截图）

每一节都要在下面 4 个条件下各走一遍并留截图，缺一张都不算过：

- [ ] 8.1 **360vp 宽度**：首页三问不截断、无横向滚动、底栏浮岛不挤压文字
- [ ] 8.2 **深色模式**：首页 / 共同时间（列表 + 周历）/ 我的 / 计划冲突卡 / 三个 Sheet / 班表页无白底残留，文字对比度正常
- [ ] 8.3 **系统字体 2.0×**：卡片不破版、不出现文字重叠；按钮文字可完整读出
- [ ] 8.4 **读屏（Screen Reader）**：三个答案、冲突归因、替代时间建议都能被读成完整一句话；状态不只靠颜色表达
