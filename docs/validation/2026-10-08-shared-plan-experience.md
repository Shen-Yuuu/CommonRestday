# 共同计划体验修复 · 2026-10-08

## 已实施

1. 空态检查成功读取的本机计划与共同计划总数；有任一种计划均不显示空态。读取失败不冒充空列表。
2. 计划页保留一个下拉刷新入口，同时读取共同计划与班表；不自动重放结果未知的写请求。只有确实存在待核实请求时保留「核实 / 重试」，它不是刷新按钮。
3. 「开启／关闭计划通知」位于「双方共同计划」标题右侧。
4. 已取消的本机／共同计划从列表移除。协议内部的取消墓碑不删除，防止迟到响应把旧计划复活；已有系统日历副本仍受原导出规则约束。
5. 本机与共同计划合成一条开始时间升序列表，确认投影不重复出现。改期申请按卡片首先展示的新申请时间排序，原确认时间仍标注并继续参与计算。
6. 共同周历读取已确认本地投影，另画带玫红描边与标题的计划块，并新增「已安排计划」图例。未确认邀请没有本地活动投影，不绘制。跨日计划按原裁剪函数分列。
7. 仅改变周历的显示，不从合并忙碌区间里减掉计划，避免抹掉真正重叠的班次／课程。确认前不占用、确认后占用、未确认改期保留旧时间的算法未更改。

## 延迟分析与优化边界

- 原发起路径：操作入口一次 `capabilities`，提交前／入队后／发送后／落地前反复读取上下文，再加传输前一次，共 6 次。现为 2 次，加一次 `mutate`。刷新为 3→2 次能力调用，加一次 `read`。
- 仍在操作入口、实际传输前验证服务端绑定与能力；每次真实读写仍携带匿名认证 token，服务端鉴权和密文校验没有移除。
- 操作内围栏改为 SDK 当前匿名 UID、本地配对世代、ACTIVE 意图与开关检查，不再为每一个本地围栏强制刷新 token、请求能力。当前 UID 查询不初始化 Auth、不创建匿名账号、不获取 token。
- 操作结果落地前仍检查会话；UID/generation 变化、能力关闭、不合法响应、密文持久化失败均不放行。
- 一次计划下拉的共同计划读与班表读并行启动，重算继续走既有串行队列；两条工作完成后才收转圈。
- 新安全日志 `FORTWO_PLAN_RPC_TIMING` 仅包含 `tag/method/elapsedMs/returned`，无参数、账号、计划内容、token 或 SDK 原始消息。`returned=true` 仅表示传输返回了可用结构，不等同于业务成功。
- 代码侧减少调用次数不等于设备侧已测得提速比例。网络与云侧执行也可能使真机变慢；不能承诺换真机必然解决。
- 云侧 `dateplan.mutate` 仍在已提交后等待一次推送投递。已有 HTTPS 请求超时上限 5 秒，但总投递还包括数据库事务；没有证据时不把它判定为这次慢的唯一原因。本次未更改通知投递策略或云端代码，避免引入新的通知到达延迟／部署要求。

## 用户双端测试步骤

不用重新部署云对象，不用重新申请权限／证书／Profile，也不要卸载、清数据或解除现有连接。

1. 在 DevEco 对 A、B 分别覆盖 Run 主项目，保留已有配对和共同计划连接。
2. 两端打开「共同 → 计划」：有计划时不出现兔子空态；标题右侧是计划通知开关，不再有普通刷新按钮。
3. A 创建一个未来邀请；B 在计划列表任意空白处向下拉。B 应看到待确认，周历尚无该计划块；A 同样不应显示“没有本机计划”。
4. B 同意；A 下拉刷新。双方切到「周历」对应日期，应看到带标题的计划块和「已安排计划」图例，而不是只能看到自己的忙碌底色。被确认的时间不再是可用空闲。双方上课／上班的其他时段不应丢失。
5. A、B 再创建不同开始时间的计划，故意先创建晚的再创建早的；刷新后整列按时间升序。若本机还有旧计划，也应按同一排序混排，不重复显示确认投影。
6. A 取消一条确认计划：A 的卡片应消失；B 下拉后卡片与周历计划块也消失，重新打开或刷新不恢复“已取消”卡片。若有系统日历导出，单独核对系统副本，不能以应用卡片消失推断系统副本自动删除。
7. 如条件允许，测试跨零点计划分列、未确认改期仍展示原确认时段、同意改期后迁移，以及最后一个计划取消后显示真正空态。
8. 测时间：分别记录 A 从创建点击到结果、B 下拉到停止转圈的秒数；紧接着再做一次下拉作为对照。若仍明显慢，在本机日志搜索 `FORTWO_PLAN_RPC_TIMING`，只发该标记的行并说明操作。不要发送 token／邀请码／认证配置全文。后续可区分能力、读取或修改哪个 RPC 慢；真实手机仍需另测。

通知审核／关闭系统通知不影响邀请与确认本身；本次验证不把“云端推送 ACK”当作锁屏到达证据。
